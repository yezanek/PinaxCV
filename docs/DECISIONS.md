# PinaxCV Architecture Decisions

Decisions made by the product owner on 2026-10-13 are recorded as ADR-009 onward. Spike results (M0.5) will be added as they land.

## ADR-001 — Standalone-first

PinaxCV v1 is Linux/Windows desktop only. This avoids recurring hosting costs before product-market evidence exists.

## ADR-002 — SQLite in v1

SQLite is the v1 persistence implementation. PostgreSQL is reserved for a future SaaS phase.

## ADR-003 — Domain independent of storage

The domain must not depend on SQLite or PostgreSQL. Persistence is behind application/repository boundaries.

## ADR-004 — Tauri as adapter

Business logic does not live in Tauri commands.

## ADR-005 — HTML export in v1

PinaxCV exports a single self-contained HTML file from `ResolvedCv`, independently of PDF rendering. It is intended for personal websites.

## ADR-006 — Separate PDF and HTML templates

PDF and HTML share semantic content but have different layout requirements. HTML is not generated by converting the PDF.

## ADR-007 — macOS deferred

macOS support is a product-validation decision, not a v1 requirement.

- CI also builds and tests on `macos-latest` as a non-blocking job (`continue-on-error`), to catch portability and WebKit differences early. A macOS failure never blocks a merge.
- No macOS signing, notarization, installers or releases until Future M10.

## ADR-008 — SaaS deferred

Accounts, HTTP API, PostgreSQL, synchronization, multi-tenancy, billing, and hosted infrastructure are not implemented until explicitly justified by demand. The intended business model is a future paid hosted version.

## ADR-009 — License and repository

Apache-2.0. Public repository `pinaxcv` from day one.

## ADR-010 — Release scope

No early-access release before AI: the first public release (1.0, milestone M8) includes AI. The AI work is split into M7a (foundation and tailoring) and M7b (rewriting, review, text import).

## ADR-011 — Languages

English only in v1, for both the UI and CV content. AI prompts still tell the model to keep the source text's language and never translate, and `LanguageChanged` still drops a rewrite that changes language, because imported or pasted text can be in another language. All UI strings go through `i18n`; headings and date formatting go through `cv-core::locale` tables so more languages can be added without restructuring.

## ADR-012 — Platforms, packaging and testing

- Development happens on Linux. CI runs on `ubuntu-22.04` and `windows-latest` from the first commit; the Windows runner (including `tauri-driver` end-to-end tests) is the Windows test machine until a manual pass in a Windows 11 evaluation VM before 1.0.
- Linux: AppImage, `.deb` and Flatpak.
- Windows: NSIS installer plus a portable exe labelled "no auto-update".
- Windows builds are unsigned before 1.0 and signed from 1.0.
- Update checks are asked on first run with "off" preselected.

## ADR-013 — Privacy rules

- Contact details are never sent to an AI provider, except by the text importer (`IMPORT_EXTRACT`), whose consent dialog shows the exact text and says contact details are included.
- The name is sent only with the opt-in `ai.send_name` setting. Location is sent as city and country only, and can be disabled.
- HTML export has "Include email" (default on) and "Include phone" (default off).
- The AI cache is included in backups; Settings has "Clear AI cache", and "Delete all data" removes it.

## ADR-014 — Security rules

- Only `https:` and `mailto:` links are clickable in PDF and HTML exports; other schemes are printed as plain text and flagged by lint.
- The backend opens every file dialog and writes only to the returned path; the UI never passes paths.
- The HTML "no external resources" test parses the output and fails on any non-`data:` resource load; navigational links are allowed.

## ADR-015 — Variant model

- A variant can hide sections, entries, bullets, skills and language items, and can reorder sections (CV id as the parent key in `order`), entries, bullets and skills. `skills_order` is removed in favour of `order`.
- Experience order can be changed manually; AI may suggest reordering only when the user enables the opt-in tailoring option.
- Text overrides cover bullets (bullet id), entry descriptions (entry id) and the summary (`summary_override`). Titles, employers, dates and locations are never overridable.
- `Entry` gains an optional `url` (certifications, projects); licence numbers go in `description`.
- `Variant` gains `schema_version` with its own migration chain.
- `ResolvedCv` keeps all entity IDs; the Typst data contract omits them.
- Fit-to-length cuts are always `Pending` for user review.
- Only base CVs get automatic snapshots. Deleted CVs are recoverable for 30 days.
- The latest AI review made without a variant is stored per CV in `review_sessions`.

## ADR-016 — Rendering

- Inter is the only CV font in v1.
- Headings are printed as written (title case), not upper-cased.
- A "Page 1 of 2" footer is included only if extraction tests prove it does not interleave with body text.
- The template places contact details in the first five extracted lines; the ATS check fails only beyond eight.
- Characters the embedded fonts cannot display raise a `MissingGlyphs` warning; export is still allowed.
- Live preview uses PNG pages served as raw bytes over a `preview://` custom URI scheme.
- HTML export: single column, system fonts, automatic dark mode, print styles.
- Absent optional fields in the Typst data contract are `null`, never empty strings.

## ADR-017 — AI providers and tests

- Providers: Anthropic, OpenAI, Gemini, and any OpenAI-compatible endpoint by base URL (covers Ollama and other local servers). There is no dedicated Ollama adapter.
- There is no default model: the user enters the model name.
- CI replays recorded AI responses; live evals run by hand before releases.

## ADR-018 — Imports

- The product owner supplies real (redacted) LinkedIn and Europass exports before M4; the importers are built against them.
- A heuristic text/PDF importer works without AI and is labelled low confidence.

## ADR-019 — Persistence details

- Synchronous `Store` trait in `cv-store`, called from async `cv-app` services via `spawn_blocking` (`cv-api` holds only DTOs and `ApiError`, see ADR-021).
- Revision, title and name columns are authoritative over the JSON copies.
- The migration test uses a synthetic v0 shape, since v1 starts at schema version 1.
- Database restore validates the file, backs up the current database, swaps and reopens.

## ADR-020 — Development workflow

Semantic branches and one PR per feature (stacked when needed), Conventional Commits, CodeRabbit review on every PR, and the product owner merges. See `AGENTS.md`.

## ADR-021 — Crate layering for application services

The spec calls `cv-api` both "types shared by src-tauri and ui" and "application services". Both cannot hold, because the UI compiles `cv-api` to WASM and services need SQLite and Typst. So:

- `cv-api`: request/response DTOs and `ApiError` only (WASM-safe).
- `cv-app` (new, native only): application services implementing the operations over `cv-core`, `cv-store`, `cv-render`, `cv-import` and `cv-ai`. Tauri commands call it; a future HTTP server could too.
- Storage-agnostic records (`StoredCv`, `CvSummary`, …) and report types (`LintIssue`, `AtsReport`, …) live in `cv-core`, since `cv-api` and the producing crates both need them.
- Seam traits live with their concern: `Store` in `cv-store` (SQLite-free signatures; the SQLite implementation sits behind it), `Exporter` and `TextExtractor` in `cv-render`, `Llm` in `cv-ai`, `PageCounter` in `cv-core`.

## ADR-022 — Typst pin and our own `World` (M0.5 spike)

- Pin `typst`, `typst-layout`, `typst-pdf` and `typst-render` at 0.15.1. `cv-render` implements its own small `World` (embedded Inter, one in-memory main file, no package downloads, `today` returns `None`); `typst-as-lib` is not used.
- The template never interpolates user text into Typst markup. The spike broke on an unescaped `@` in an email address (read as a label), so `cv-render` passes the `ResolvedCv` as data (`sys.inputs` / JSON) and the template reads fields from it.
- Measured with `spikes/typst-pdf` (1-page CV, Inter 4.1, release build, GitHub runners): cold compile 7.4 ms (Linux), 7.2 ms (Windows), 406 ms (macOS, first run on a cold runner); PDF export 2.2 / 2.9 / 14.8 ms; 31,274 bytes.

## ADR-023 — Deterministic PDF output (M0.5 spike)

- Export with `PdfOptions { ident: Smart::Custom(..), timestamp: None }`. The same input produced byte-identical PDFs within a run and across Linux, Windows and macOS (SHA-256 prefix `de88d17d5050738c` on all three).
- Golden-file tests in M2 may therefore compare PDF bytes, not only extracted text. A Typst upgrade that changes bytes is expected and updates the golden files in the same PR.

## ADR-024 — PDF text read-back for the ATS check (M0.5 spike)

- `cv-render`'s `TextExtractor` uses `lopdf` (0.45). It keeps line breaks, so the header checks (name in the first 3 lines, email and phone in the first 8) work: the email was on line 3. Every checked string survived on all three systems, with no ligature, private-use or replacement codepoints when ligatures are off.
- `pdf-extract` (0.12) also recovers every string but joins the header lines into one line ("Jane DoeBackend Engineer…"), which is what naive ATS parsers may see. The template therefore ends each header line with a trailing non-breaking space so words stay separated even for line-joining extractors; an M2 test runs both extractors and fails if header words merge.
- The planned fallback (a minimal PinaxCV-specific reader, scored "as read by PinaxCV") is not needed for now.

## ADR-025 — Live preview and desktop shell build (M0.5 spike)

- Preview stays PNG over a custom `preview` URI scheme (`preview://localhost/…` on Linux and macOS, `http://preview.localhost/…` on Windows). Incremental recompile after editing one bullet: p50 0.4 ms (Linux), 0.7 ms (Windows), 0.6 ms (macOS). PNG render of page 1 at 1.5 px/pt: p50 10.9 / 8.3 / 13.9 ms, about 100 KB. Compile plus render is under 30 ms at p90 on every runner, far inside the spec's p95 < 250 ms target after the 150 ms debounce, so SVG preview is not needed. The 2-page CV measurement is repeated in M2 with the real template.
- Tauri 2.12 + Leptos 0.8 (CSR) + Trunk 0.21 builds on `ubuntu-22.04` and `windows-latest` (Linux needs `libwebkit2gtk-4.1-dev`, `libsoup-3.0-dev`, `librsvg2-dev`, `libayatana-appindicator3-dev`). Cold CI builds: Trunk 55 s / 216 s, Tauri shell 119 s / 239 s (Linux / Windows). On Linux the app was run under Xvfb and showed the page served over `preview://`.
- The CSP allows `img-src 'self' preview: http://preview.localhost` and `script-src 'self' 'wasm-unsafe-eval'`; M3 keeps exactly these additions.

## Open decisions

- Tagged PDF (accessibility tags) for the pinned Typst version (M2).
- Exact HTML CSS/template design (M2).
- Future SaaS DTO reuse and synchronization model (SaaS phase).
