# PinaxCV Architecture Decisions

Decisions made by the product owner on 2026-10-13 are recorded as ADR-009 onward. Spike results (M0.5) will be added as they land.

## ADR-001 — Standalone-first

PinaxCV v1 is Linux/Windows desktop only. This avoids recurring hosting costs before product-market evidence exists.

## ADR-002 — SQLite in v1

SQLite is the v1 persistence implementation. PostgreSQL is reserved for a future SaaS phase.

## ADR-003 — Domain independent of storage

The domain must not depend on SQLite or PostgreSQL. Persistence is behind application/repository boundaries.

## ADR-004 — Tauri as adapter

Business logic does not live in Tauri commands.

## ADR-005 — HTML export in v1

PinaxCV exports a single self-contained HTML file from `ResolvedCv`, independently of PDF rendering. It is intended for personal websites.

## ADR-006 — Separate PDF and HTML templates

PDF and HTML share semantic content but have different layout requirements. HTML is not generated by converting the PDF.

## ADR-007 — macOS deferred

macOS support is a product-validation decision, not a v1 requirement.

- CI also builds and tests on `macos-latest` as a non-blocking job (`continue-on-error`), to catch portability and WebKit differences early. A macOS failure never blocks a merge.
- No macOS signing, notarization, installers or releases until Future M10.

## ADR-008 — SaaS deferred

Accounts, HTTP API, PostgreSQL, synchronization, multi-tenancy, billing, and hosted infrastructure are not implemented until explicitly justified by demand. The intended business model is a future paid hosted version.

## ADR-009 — License and repository

Apache-2.0. Public repository `pinaxcv` from day one.

## ADR-010 — Release scope

No early-access release before AI: the first public release (1.0, milestone M8) includes AI. The AI work is split into M7a (foundation and tailoring) and M7b (rewriting, review, text import).

## ADR-011 — Languages

English only in v1, for both the UI and CV content. AI prompts still tell the model to keep the source text's language and never translate, and `LanguageChanged` still drops a rewrite that changes language, because imported or pasted text can be in another language. All UI strings go through `i18n`; headings and date formatting go through `cv-core::locale` tables so more languages can be added without restructuring.

## ADR-012 — Platforms, packaging and testing

- Development happens on Linux. CI runs on `ubuntu-22.04` and `windows-latest` from the first commit; the Windows runner (including `tauri-driver` end-to-end tests) is the Windows test machine until a manual pass in a Windows 11 evaluation VM before 1.0.
- Linux: AppImage, Flatpak and Snap (ADR-049 replaced `.deb` with Snap).
- Windows: NSIS installer plus a portable exe labelled "no auto-update".
- Windows builds are unsigned before 1.0 and signed from 1.0.
- Update checks are asked on first run with "off" preselected.

## ADR-013 — Privacy rules

- Contact details are never sent to an AI provider, except by the text importer (`IMPORT_EXTRACT`), whose consent dialog shows the exact text and says contact details are included.
- The name is sent only with the opt-in `ai.send_name` setting. Location is sent as city and country only, and can be disabled.
- HTML export has "Include email" (default on) and "Include phone" (default off).
- The AI cache is included in backups; Settings has "Clear AI cache", and "Delete all data" removes it.

## ADR-014 — Security rules

- Only `https:` and `mailto:` links are clickable in PDF and HTML exports; other schemes are printed as plain text and flagged by lint.
- The backend opens every file dialog and writes only to the returned path; the UI never passes paths.
- The HTML "no external resources" test parses the output and fails on any non-`data:` resource load; navigational links are allowed.

## ADR-015 — Variant model

- A variant can hide sections, entries, bullets, skills and language items, and can reorder sections (CV id as the parent key in `order`), entries, bullets and skills. `skills_order` is removed in favour of `order`.
- Experience order can be changed manually; AI may suggest reordering only when the user enables the opt-in tailoring option.
- Text overrides cover bullets (bullet id), entry descriptions (entry id) and the summary (`summary_override`). Titles, employers, dates and locations are never overridable.
- `Entry` gains an optional `url` (certifications, projects); licence numbers go in `description`.
- `Variant` gains `schema_version` with its own migration chain.
- `ResolvedCv` keeps all entity IDs; the Typst data contract omits them.
- Fit-to-length cuts are always `Pending` for user review.
- Only base CVs get automatic snapshots. Deleted CVs are recoverable for 30 days.
- The latest AI review made without a variant is stored per CV in `review_sessions`.

## ADR-016 — Rendering

- Inter is the only CV font in v1.
- Headings are printed as written (title case), not upper-cased.
- A "Page 1 of 2" footer is included only if extraction tests prove it does not interleave with body text.
- The template places contact details in the first five extracted lines; the ATS check fails only beyond eight.
- Characters the embedded fonts cannot display raise a `MissingGlyphs` warning; export is still allowed.
- Live preview uses PNG pages served as raw bytes over a `preview://` custom URI scheme.
- HTML export: single column, system fonts, automatic dark mode, print styles.
- Absent optional fields in the Typst data contract are `null`, never empty strings.

## ADR-017 — AI providers and tests

- Providers: Anthropic, OpenAI, Gemini, and any OpenAI-compatible endpoint by base URL (covers Ollama and other local servers). There is no dedicated Ollama adapter.
- There is no default model: the user enters the model name.
- CI replays recorded AI responses; live evals run by hand before releases.

## ADR-018 — Imports

- The product owner supplies real (redacted) LinkedIn and Europass exports before M4; the importers are built against them.
- A heuristic text/PDF importer works without AI and is labelled low confidence.

## ADR-019 — Persistence details

- Synchronous `Store` trait in `cv-store`, called from synchronous `cv-app` services; the Tauri shell wraps each call in `spawn_blocking` (ADR-036). `cv-api` holds only DTOs and `ApiError` (ADR-021).
- Revision, title and name columns are authoritative over the JSON copies.
- The migration test uses a synthetic v0 shape, since v1 starts at schema version 1.
- Database restore validates the file, backs up the current database, swaps and reopens.

## ADR-020 — Development workflow

Semantic branches and one PR per feature (stacked when needed), Conventional Commits, CodeRabbit review on every PR, and the product owner merges. See `AGENTS.md`.

## ADR-021 — Crate layering for application services

The spec calls `cv-api` both "types shared by src-tauri and ui" and "application services". Both cannot hold, because the UI compiles `cv-api` to WASM and services need SQLite and Typst. So:

- `cv-api`: request/response DTOs and `ApiError` only (WASM-safe).
- `cv-app` (new, native only): application services implementing the operations over `cv-core`, `cv-store`, `cv-render`, `cv-import` and `cv-ai`. Tauri commands call it; a future HTTP server could too.
- Storage-agnostic records (`StoredCv`, `CvSummary`, …) and report types (`LintIssue`, `AtsReport`, …) live in `cv-core`, since `cv-api` and the producing crates both need them.
- Seam traits live with their concern: `Store` in `cv-store` (SQLite-free signatures; the SQLite implementation sits behind it), `Exporter` and `TextExtractor` in `cv-render`, `Llm` in `cv-ai`, `PageCounter` in `cv-core`.

## ADR-022 — Typst pin and our own `World` (M0.5 spike)

- Pin `typst`, `typst-layout`, `typst-pdf` and `typst-render` at 0.15.1. `cv-render` implements its own small `World` (embedded Inter, one in-memory main file, no package downloads, `today` returns `None`); `typst-as-lib` is not used.
- The template never interpolates user text into Typst markup. The spike broke on an unescaped `@` in an email address (read as a label), so `cv-render` passes the `ResolvedCv` as data (`sys.inputs` / JSON) and the template reads fields from it.
- Measured with `spikes/typst-pdf` (1-page CV, Inter 4.1, release build, GitHub runners): cold compile 7.4 ms (Linux), 7.2 ms (Windows), 406 ms (macOS, first run on a cold runner); PDF export 2.2 / 2.9 / 14.8 ms; 31,274 bytes.

## ADR-023 — Deterministic PDF output (M0.5 spike)

- Export with `PdfOptions { ident: Smart::Custom(..), timestamp: None }`. The same input produced byte-identical PDFs within a run and across Linux, Windows and macOS (SHA-256 prefix `de88d17d5050738c` on all three).
- Golden-file tests in M2 may therefore compare PDF bytes, not only extracted text. A Typst upgrade that changes bytes is expected and updates the golden files in the same PR.

## ADR-024 — PDF text read-back for the ATS check (M0.5 spike)

- `cv-render`'s `TextExtractor` uses `lopdf` (0.45). It keeps line breaks, so the header checks (name in the first 3 lines, email and phone in the first 8) work: the email was on line 3. Every checked string survived on all three systems, with no ligature, private-use or replacement codepoints when ligatures are off.
- `pdf-extract` (0.12) also recovers every string but joins the header lines into one line ("Jane DoeBackend Engineer…"), which is what naive ATS parsers may see. The template therefore ends each header line with a trailing non-breaking space so words stay separated even for line-joining extractors; an M2 test runs both extractors and fails if header words merge.
- The planned fallback (a minimal PinaxCV-specific reader, scored "as read by PinaxCV") is not needed for now.

## ADR-025 — Live preview and desktop shell build (M0.5 spike)

- Preview stays PNG over a custom `preview` URI scheme (`preview://localhost/…` on Linux and macOS, `http://preview.localhost/…` on Windows). Incremental recompile after editing one bullet: p50 0.4 ms (Linux), 0.7 ms (Windows), 0.6 ms (macOS). PNG render of page 1 at 1.5 px/pt: p50 10.9 / 8.3 / 13.9 ms, about 100 KB. Compile plus render of page 1 is under 30 ms at p90 on every CI runner. These numbers are preliminary: the spec's target (p95 < 250 ms after the 150 ms debounce, two-page CV, mid-range laptop) is only marked as met once M2 measures it with the real template. On this evidence PNG preview is kept and SVG preview is not pursued.
- Tauri 2.12 + Leptos 0.8 (CSR) + Trunk 0.21 builds on `ubuntu-22.04` and `windows-latest` (Linux needs `libwebkit2gtk-4.1-dev`, `libsoup-3.0-dev`, `librsvg2-dev`, `libayatana-appindicator3-dev`). Cold CI builds: Trunk 55 s / 216 s, Tauri shell 119 s / 239 s (Linux / Windows). On Linux the app was run under Xvfb and showed the page served over `preview://`.
- The CSP allows `img-src 'self' preview: http://preview.localhost` and `script-src 'self' 'wasm-unsafe-eval'`; M3 keeps exactly these additions.

## ADR-026 — Building from source on Linux, macOS and Windows

- The product owner builds PinaxCV from source on a Linux laptop and a MacBook, so `docs/BUILDING.md` documents the system packages for Debian/Ubuntu, Fedora, Arch, macOS and Windows, the Rust and tool versions CI uses, and the build, test and check commands.
- A milestone that changes how PinaxCV is built (new system library, new tool, the app in M3, packaging in M8) updates `docs/BUILDING.md` in the same PR.
- Supporting a macOS source build does not change ADR-007: no macOS release, signing or notarization in v1. A local `cargo tauri build` on macOS gives an unsigned app for the builder's own machine.
- Fedora and Arch are not tested in CI; their package lists follow the Tauri 2 prerequisites and are checked by hand.

## ADR-027 — Validation details (M1)

- `validate::for_save` mutates the CV: out-of-range template options are clamped, a non-finite option takes its default, and an accent that is not `#RRGGBB` is reset to black. Each change is a warning. Duplicate IDs, months outside 1..=12 and a stale `schema_version` are errors, and the store refuses to save a CV with errors.
- An end date before the start date is content, not structure, so it is left to lint (spec section 7.1) and never blocks a save.
- `validate::for_export` repeats the structural checks and requires a non-blank full name and a non-blank email or phone. It does not clamp, because export works on the saved document.

## ADR-028 — Resolve and prune details (M1)

- Hiding a section or a skill group hides everything under it. A skill group with no visible skills is omitted like an empty section, so the PDF never prints an empty group label. A section that is empty in the base CV is omitted too.
- A summary override replaces the base summary; with no override the base summary is used.
- `order` lists skip unknown and repeated IDs. Children that are not listed follow in base order.
- `Variant::prune(&mut self, &Cv)` removes stale references and returns the removed IDs. It also removes references to the wrong kind of entity (a bullet in `collapsed`, a language item in `text_overrides`, a child listed under the wrong parent). Suggestions are not pruned; their targets are checked when a suggestion is accepted (M5).
- The idempotence property (spec 4.4, d) is tested by turning the resolved output back into a base CV and resolving it with an empty variant. `collapsed` is a rendering flag, so it is not compared.

## ADR-029 — Lint details (M1)

- `missing_glyphs` is reported by `cv-render` as a compile `Diagnostic`, because only the renderer knows which characters the embedded fonts cover. The API layer adds it to the `lint` command's results (M2/M3). `cv_core::lint` implements every other rule in spec section 7.1.
- A year-only date overlaps every month of its year: `date_order` never fires for an end and a start in the same year when one of them has no month, and `gap` uses the shortest possible gap (a year-only end counts as December, a year-only start as January). Overlapping and current jobs cover the months they span.
- `date_style_mixed` flags every entry that prints a year-only date when any other printed date has a month.
- `duplicate_bullet` and `weak_opening` compare after collapsing whitespace and lower-casing. `special_chars` covers control characters other than newline and tab, private-use characters, the emoji blocks U+1F000..U+1FAFF and U+2600..U+27BF, U+FE0F and U+200D.
- Collapsed entries are not flagged by `no_bullets`, since hiding their bullets was the user's choice.
- Findings are ordered by the spec's table, then by document order.

## ADR-030 — Fit-to-length details (M1)

- `fit` takes an `&mut dyn IdSource` for the suggestion IDs and returns `Result<FitResult, PageCountError>`, so a render failure is reported instead of being mistaken for a page count. `FitResult::Fits { pages, cuts }` carries the pending cuts; `CannotFit { pages }` carries none.
- `RelevanceScores` (per entry, bullet and skill, 0..=100) is a plain lookup in `cv-core`; `cv-ai` fills it from the relevance stage (spec 11.5).
- Unscored bullets have priority 50 and ties go to the bullet latest in the document, which gives the spec's position rule: later bullets of older entries go first.
- "Collapse instead" applies to the last visible bullet of an entry whose relevance is below 40, or unscored. Entries at 40 or above keep their heading and lose the bullet. Locked entries are never collapsed.
- The most recent experience entry is the current one, else the one with the latest start date.
- A cut's reason is "Removed to fit N page(s)" for both hidden bullets and collapsed entries. A page target of 0 counts as 1. After 200 rounds, `fit` reports `CannotFit` unless the last cut made it fit.

## ADR-031 — SQLite store details (M1)

- `rusqlite` 0.40 with the `bundled` feature, so every platform gets the same SQLite (3.27 or newer is needed for `VACUUM INTO`) and Windows needs no system library. Database schema migrations are SQL files applied in order, each in a transaction, with `PRAGMA user_version` as the counter. A database newer than the app is refused with `NewerSchema`.
- The store injects a `Clock` and writes RFC 3339 UTC timestamps with milliseconds (`2026-10-13T15:03:33.120Z`) in a fixed width, so SQL text comparison is time order. No date-time crate is needed.
- `create_cv`, `save_cv`, `duplicate_cv` and `restore_snapshot` run `validate::for_save` and refuse a CV with structural errors (ADR-027). Variants are stored as given; `Variant::prune` is the UI's job.
- A soft-deleted CV and its variants and snapshots are invisible (`NotFound`) until restored; `purge_deleted` removes them for good, and foreign keys cascade.
- `duplicate_cv` copies the base CV only, with fresh IDs (`Cv::with_fresh_ids`); variants are not copied, because their IDs would no longer match. `duplicate_variant` gives the copy and its suggestions fresh IDs.
- Export snapshots are skipped when the CV already has one from the last hour, so `add_snapshot` can be called on every export. Only the latest 50 snapshots per CV are kept. Restoring a snapshot keeps the current title, because the title column is authoritative.
- `SqliteStore::restore_from(path)` checks the backup (opens read-only, `PRAGMA integrity_check`, schema version 1..=current), saves the live database next to itself as `<name>.before-restore-<timestamp>`, closes the connection, removes the `-wal` and `-shm` files, copies the backup in and reopens. It is a method of `SqliteStore`, not of `Store`, because it is about database files.
- `CvSummary::page_count` is `None` until M2 records the last render's page count.
- Contract tests use only `&dyn Store`; the few tests that need raw SQL (migration of v0 content, user_version) live inside the crate.

## ADR-032 — Typst renderer (M2)

- `cv-render` embeds Inter (regular, bold, semibold, italic) and the `classic` template. The Typst World resolves only `template.typ` and the virtual `data.json`; every other file read is denied, there are no system fonts and no packages, and `today()` is `None`.
- PDFs are tagged (`PdfOptions::tagged`, on by default in Typst 0.15.1) with no timestamp, a fixed identifier and no creator string, so the same input gives the same bytes. Title is "<Full name>, CV" and author the full name, set from `data.json`.
- Before each compile, every printed character is checked against the embedded fonts' coverage; uncovered characters give one `missing_glyphs` warning (the first 20 listed). The CJK fixture triggers it; the Latin, Greek and Cyrillic fixture does not.
- The template prints the period and location on a second line under "title, org" (spec 6.4 rule 1), uses real headings and lists, and only `https:`/`mailto:` URLs become links (the `clickable` flag in `data.json`).
- One `Renderer` per process behind a mutex. `PageCounter for Renderer` compiles with the default export options.

## ADR-033 — ATS check details (M2)

- `cv_render::ats::ats_report` returns the `cv_core::AtsReport` that `cv-api` already carries. It reads the PDF with `LopdfExtractor` (ADR-024) and compares it with the same template data the PDF was rendered from, so headings, dates and skipped blank fields match what is printed. `ats_report_with` takes any `TextExtractor`.
- Seven checks: `name_at_top`, `contact_at_top`, `section_headings`, `entry_details`, `clean_characters`, `bullets`, `reading_order`. The score is the rounded share of passed checks. If the text cannot be read at all, the report has one failed `text_extracted` check and a score of 0.
- A section heading must be a line of its own. Bullets match after whitespace is collapsed, or, for a long word such as a URL that wraps without a hyphen, with all whitespace removed.
- Contact header lines end with a no-break space, so line-joining extractors such as `pdf-extract` keep the words apart. The golden suite checks this with `pdf-extract`.
- The `cjk` fixture is the one expected failure. Inter has no CJK glyphs, so the export reports `missing_glyphs` and the ATS check fails on replacement characters instead of passing silently. CJK fonts are out of scope for v1.
- Extracted-text snapshots live in `crates/cv-render/tests/snapshots/` and are checked out with LF line endings on every platform.

## ADR-034 — HTML export details (M2)

- `HtmlExporter` and `to_html` build the page from the same template data as the PDF (`to_typst_data`), so both formats print the same headings, dates, contact choices and link rules. The HTML template is separate Rust code plus one stylesheet, `templates/html/cv.css`.
- Structure: `header` with an `h1` name, headline and contact list; `main` with one `section` and `h2` per CV section; one `article` and `h3` per entry (`h2` in a section without a title, so no level is skipped); real lists for bullets, skills and languages. A custom section without a title has no `h2`. The `ExportOptions::html_default()` starting choices are email on, phone off; the app passes the user's dialog choices. The keyboard focus outline uses the text colour, so it stays visible whatever the accent.
- Every piece of user text, including attribute values, escapes `& < > " '`. A stored accent is used only if it is `#RRGGBB`; anything else falls back to the text colour, so a bad value cannot inject CSS.
- The email is a `mailto:` link. Phone, location and every non-`https:`/`mailto:` URL are plain text.
- Styling: single column up to 46rem, system font stack, light and dark through `prefers-color-scheme`, a narrow-screen rule and a print stylesheet. No scripts, web fonts or images.
- Tests parse each fixture's tags and attributes (loading tags, `src`/`srcset`/`poster`/`data` with any spacing around `=`) and the CSS in `<style>` and `style` attributes (`@import`, non-`data:` `url(`), never text between tags, check every `href`, and snapshot the body of each fixture's HTML with the dialog defaults (email on, phone off).

## ADR-035 — Preview and export speed with the real template (M2)

- `cargo run --release -p cv-render --example preview_latency` edits one bullet, then resolves, compiles and renders every page to PNG at 1.5 px/pt, 40 times. It uses the 3-page `long` fixture, which is harder than the spec's 2-page CV.
- In a 4-core Linux cloud container: preview p50 136 ms, p95 179 ms (target p95 < 250 ms after the debounce); PDF export of `typical` p95 2.4 ms (target < 1 s); HTML export of `typical` p95 0.07 ms (target < 250 ms).
- Nearly all preview time is PNG rendering of every page, not compilation (ADR-025 measured incremental compiles under 1 ms). If a slower laptop misses the target, M3 renders only the visible pages first; that is not needed on this evidence.
- The spec's reference machine is a mid-range laptop, so the target is marked met on this evidence and re-checked on the product owner's machines with the command above.

## ADR-036 — Application services in `cv-app` (M3)

- `cv_app::App` implements the CV, variant, preview, export, ATS and lint operations of spec section 10.2 on top of `Store`, `Renderer` and the exporters. The methods are synchronous; the Tauri shell runs each call in `spawn_blocking`, which is where ADR-019's async boundary now sits. This keeps `cv-app` free of an async runtime and of Tauri, and the boundary check forbids Tauri in it.
- File dialogs are the `FileDialog` trait (save and open), implemented by the shell with the Rust-side dialog plugin. The UI never sends a path. A cancelled dialog returns `ErrorCode::Cancelled`. Files are written to a hidden temporary file next to the target and renamed over it, so a failed export leaves nothing half-written. Each export creates its own uniquely named temporary file exclusively. On Unix it is created `0600` and takes over the replaced file's permissions; the folder is synced after the rename. Write errors say only the error kind, never the path, because the path usually holds the user's name.
- `save_cv` runs `validate::for_save` (clamping options) and refuses structural errors with `Validation`, carrying every issue in `details`. Exports run `validate::for_export` first. A PDF export also returns the ATS report of the written bytes.
- `preview` renders unsaved editor state without saving it and keeps only the newest preview's PNG pages for the `preview://` handler (`{base}/{preview_id}/{page}.png`, 1-based). The preview id is an app-wide counter taken before rendering, not the editor's revision, so two CVs at the same revision never share pages. A slow preview finishing after a later one is not cached; `PreviewResponse.revision` still echoes the editor's revision so the UI can drop stale responses.
- `create_cv` makes a blank CV (title trimmed, "Untitled CV" if empty) with no sections. Templates for new CVs come later.
- After a successful export, an export snapshot is requested; it is best effort because the file is already written, and the store throttles it to one per hour (ADR-031).
- New IDs come from `UlidIds` (the `ulid` crate). Store and render errors map to `ApiError` codes without CV content in the message.

## ADR-037 — Desktop shell (M3)

- `src-tauri` (package `pinaxcv`) is a workspace member on Tauri 2.12 with `tauri-plugin-dialog` 2.8. It opens `pinaxcv.sqlite3` in the platform app data folder (identifier `dev.pinaxcv.app`), builds `cv_app::App` and manages it as shared state.
- Every command is a one-line adapter that runs the matching `App` method through `spawn_blocking` (ADR-036). Arguments and results are `cv-api` and `cv-core` types; errors are `ApiError`.
- `build.rs` declares the app's commands in an app manifest, so Tauri generates `allow-*` permissions for exactly those commands, and `capabilities/main.json` grants them to the main window. No dialog, fs or shell permission is granted to the webview; the save dialog runs from Rust on the blocking pool. The CSP is spec section 10.3's plus the `http://preview.localhost` origin from ADR-025.
- `preview://localhost/{preview_id}/{page}.png` (`http://preview.localhost/...` on Windows) serves PNG bytes from the newest preview with `Cache-Control: no-store`: 404 for a replaced page, 503 before startup finishes.
- Until the Leptos UI lands, `frontendDist` points at a static placeholder page so the shell builds and runs on its own. The Linux CI job now installs `libwebkit2gtk-4.1-dev`, `libsoup-3.0-dev`, `librsvg2-dev` and `libayatana-appindicator3-dev`, which is what building and testing the shell needs. `docs/BUILDING.md` lists Tauri's full prerequisite set for local builds, which also has `libxdo-dev` and `libssl-dev`; `libsoup-3.0-dev` comes in there as a dependency of `libwebkit2gtk-4.1-dev`.

## ADR-038 — Editor UI foundation (M3)

- `ui/` (package `pinaxcv-ui`) is a Leptos 0.8 CSR app built by Trunk into `ui/dist`, which the shell embeds (`frontendDist`). It is a workspace member, so `cargo build --workspace` needs `trunk build` first; CI runs Trunk before Clippy and lints the UI for `wasm32-unknown-unknown`.
- The UI calls commands through Tauri's global `invoke` (`withGlobalTauri`), with `cv-api` and `cv-core` types on both sides. Tauri expects camelCase argument names, so command parameters are single words (`id`, `req`, `target`) wherever possible.
- This first screen set covers the CV list (create, open, delete) and an editor for the title, contact fields and summary, with the live preview on the right. Each edit bumps a local counter; the preview runs 150 ms after the last edit and autosave 600 ms after (spec section 12), and preview answers for older edits are ignored. While a newer preview renders, the old pages stay dimmed with a small spinner. Only one save runs at a time; an edit made during a save is sent next with the returned revision. Export and "← CVs" first wait until the newest edit is saved, and a failed save cancels them and shows the error. A save conflict is shown, not overwritten. New CV is disabled while a create request runs.
- Checked by hand under Xvfb on Linux: creating a CV, typing the name and email updates the preview and saves, and the data is there after a restart. Sections, entries, the Style tab and keyboard shortcuts are the next M3 changes; `tauri-driver` smoke tests come with them.

## ADR-039 — Editing sections, entries and bullets (M3)

- The editor adds and removes work experience, education and project sections, their entries and bullets, and edits entry title, organisation, location and bullet text. Dates, descriptions, links, reordering, skills and languages follow in the next M3 changes.
- New IDs are ULIDs made in the UI from `Date.now()` and `crypto.getRandomValues` (`ui/src/ids.rs`), so adding an item needs no extra round trip. The encoding is unit-tested; the store still refuses duplicate IDs (ADR-027).
- Section, entry and bullet lists are keyed by ID and each input reads its value by ID, so an edit never rebuilds the field being typed in. Checked under Xvfb: typing a title, organisation and bullet keeps focus and updates the preview.

## ADR-040 — Entry dates, description and link (M3)

- Entry start and end dates are typed as `YYYY`, `YYYY-MM`, `MM/YYYY` or `M/YYYY` (years 1900 to 2100, `ui/src/dates.rs`, unit-tested). The model changes only when the text parses or is cleared, so a half-typed date never reaches autosave or the preview.
- A "current" checkbox sets the entry's ongoing flag; the renderer prints "Present" as the end.
- Each entry also edits its description and link text. Link scheme rules stay in the exporters (ADR-034).
- Checked under Xvfb: typing `2021-03` shows "Mar 2021" in the preview.

## ADR-041 — Reordering sections, entries and bullets (M3)

- Sections, entries and bullets get ↑ and ↓ buttons that swap the item with its neighbour (`ui/src/order.rs`, unit-tested). Buttons rather than drag and drop: they work from the keyboard, need no extra library and behave the same in WebKitGTK and WebView2. Drag and drop can come later on top of the same `shift` helper.
- Lists stay keyed by ID, so moving an item moves its fields without rebuilding them. Checked under Xvfb: moving a bullet up reorders the form and the preview.

## ADR-042 — Editing skills and languages (M3)

- Skills sections hold groups, each with an optional label and its skills typed as one comma-separated line. `merge_skills` (`ui/src/lists.rs`, unit-tested) keeps each position's existing ID, so renaming a skill keeps variant references to it; inserting a name in the middle shifts the IDs after it, which is acceptable until skills get their own rows.
- Languages are rows of name and level. Text fields keep what is typed (spaces included) and trim when they lose focus, like the basics fields.
- Skill groups and language rows have their own ↑ ↓ buttons (ADR-041), as the spec asks for every editor list.
- The form shows entry sections first, then skills and languages. Section order in the CV (and preview) is set with the ↑ ↓ buttons (ADR-041).
- Checked under Xvfb: adding a skills group updates the preview.

## ADR-043 — Europass PDFs are imported from their embedded XML (M4)

- The Europass editor's PDF export embeds the structured CV as an XML attachment in the current `Candidate` format (namespace `http://www.europass.eu/1.0`, HR-XML based). Checked against a real export supplied by the product owner, which is not committed.
- This refines spec section 9.2: a Europass PDF is imported from that attachment, exactly, and `UnsupportedFormat` is returned only when no Europass XML is embedded (for example a printed or scanned CV).
- `cv_import::embedded_xml` checks every embedded file and returns the first whose XML parses with a `Candidate` root element in the Europass namespace (roxmltree), whatever its file name. PDFs over 20 MB are refused before parsing. Attachments over 10 MB (spec section 9) are refused by declared size before decompressing, and decompression itself stops at 10 MB (lopdf `get_plain_content_with_limit`), so a decompression bomb cannot exhaust memory. A bare XML file is limited only by the 20 MB input cap.
- A LinkedIn "Save to PDF" profile has no embedded data and is read by the generic text importer (ADR-047).
- Tests build synthetic PDFs in code; personal data never enters the repository.

## ADR-044 — Reading the Europass Candidate XML (M4)

- `cv_import::parse_candidate` reads the Europass `Candidate` XML into plain records (person, positions, education, languages). Mapping those records to a CV, and merging, are separate steps.
- Elements are matched by local name, so the `hr:`, `oa:` and `eures:` prefixes don't matter, and unknown elements are ignored (spec section 9.2). Field paths were checked against a real export, which is not committed. Tests use synthetic XML in the same shape.
- Only the candidate's own contact channels are read. Organisation contacts and the `CandidateSupplier` block are ignored. Birth date, gender and nationality are never read, because the CV model has no fields for them.
- Descriptions are stored as escaped HTML. `html_text` drops every tag without interpreting it and splits the text into paragraphs and list items, which become bullets.
- The executive summary is a single text field, so its list items are kept as "- item" lines after the paragraphs rather than dropped.
- Every text value is normalized as spec section 9 requires: Unicode NFC (unicode-normalization 0.1.25, already locked through other dependencies), control characters stripped, whitespace collapsed and trimmed.
- XML parsing uses roxmltree 0.21.1 (added in ADR-043 for the attachment check), which the workspace already locks through Typst. It is pure Rust and needs no system libraries.

## ADR-045 — CvPartial and the Europass mapping (M4)

- `CvPartial` (in `cv-import`) has optional header fields, plus links, a summary and sections built from `cv-core` types with fresh IDs. `ImportResult` pairs it with user-readable `ImportWarning`s (spec section 9).
- `to_partial` maps Europass records as follows:
  - positions become one Experience section, and description list items become bullets;
  - education becomes one Education section, with the degree as the title;
  - languages become one Languages section, whose level is the most common CEFR score (the highest on a tie);
  - the person's and each position's location is "City, CC", or whichever of the two is known (education has no country);
  - the first email and phone are used, with a warning when there are more.
- Dates accept exactly `YYYY`, `YYYY-MM` and `YYYY-MM-DD`; the day is checked, then dropped. A date that can't be read is left empty and reported as a warning.
- Language codes map to English names for common ISO 639 codes. Other codes are kept as written.
- Checked locally against the real export: it maps into 3 sections with no warnings.

## ADR-046 — Merging an import with manual conflict choices (M4)

- The product owner asked to merge imports from two sources by hand. `cv_import::merge` applies a `MergePlan`:
  - **Header fields** (name, headline, email, phone, location, summary): `field_conflicts` lists the fields both sides fill with different values, ignoring case and spacing. The base value is kept unless the user picks "use imported". A field that is empty (or blank) on one side takes the filled value without asking; a blank imported value never overwrites anything. This extends spec section 9.5 to the header fields.
  - **Entries**: each imported entry gets Skip, Add as new or Replace. `suggest_matches` pairs entries by normalized organisation, title and start year within the same kind of section (spec section 9.5). Replace keeps the base entry's ID, so variant references to the entry survive. With no decision, an entry is added as new.
  - **Skills and languages** are merged as a union by case-insensitive name; duplicate incoming skills are dropped first. A language level is filled in only when the base has none.
  - **Links** are merged as a union by URL.
- Nothing in the base is deleted unless Replace is chosen. The caller takes a snapshot before merging (spec section 9.5).

## ADR-047 — Generic PDF text importer (M4)

- The product owner asked that any PDF be importable, as Workday-style parsers do it, in addition to the Europass importer, which stays a must-have. A PDF is tried as Europass first (ADR-043). Only a PDF without Europass data goes to the text importer.
- The text importer reads the page text in content order (`page_text`) and splits it at standard CV headings and their common synonyms (`split_sections`). It drops blank lines and "Page N of M" footers, and a repeated heading continues its section.
- `text_to_partial` builds the `CvPartial`. A date range line ("March 2021 - Present", "(2010 - 2014)", no-break spaces allowed) marks an entry, and the two lines before it are the organisation and title (LinkedIn order). A short first line after it is the location, and the rest is the description. Education entries are school and degree line pairs. Languages read "Name (Level)". Contact gives the email and phone.
- LinkedIn's sidebar comes before the name in content order. When the text starts with sidebar sections, the last three lines of the last sidebar section become the name, headline and location, with a warning. If that section has fewer than three lines it is left as it is. Skills and certifications are reported as not imported yet. Every guess is an `ImportWarning`, and the result goes through the same merge review (ADR-046).

## ADR-048 — Variant screen in the editor (M5)

- A "Version" selector above the form picks the base CV or a variant. Text edits always change the base CV; the variant panel only changes what the selected variant hides or collapses.
- The panel lists every item a variant can hide (ADR-015): sections, entries and their bullets, skill groups and their skills, and language items. Only entries can be collapsed to one line.
- Overlay edits save one at a time. An edit made while a save is in flight is sent next with the revision that save returned. The selector, "New variant" and "Delete" are disabled while a save runs, so the queue only holds the selected variant.
- Export and "← CVs" wait for both the CV save and the variant save queue, because export reads the variant from storage. If a variant save fails, the export or leave is dropped and the error is shown.
- Preview requests have their own counter, so selecting a variant re-renders without affecting the CV's autosave.
- A delete confirmation remembers the variant it was opened for; changing the selection cancels it.
- UI strings were literal English at first; they moved into the `i18n` module with ADR-050.

## ADR-049 — Linux packages: AppImage, Flatpak and Snap

- Status: accepted (Dan, 2026-10-15).
- Linux ships as AppImage, Flatpak and Snap. The `.deb` package is dropped.
- Debian and Ubuntu users install the Snap, the Flatpak or the AppImage instead.
- Changes spec section 14 and the M8 acceptance criteria. Tracked in #33 (Flatpak), #34 (Snap) and #68 (AppImage).

## ADR-050 — UI strings in one i18n module

- Every user-facing UI string lives in `ui/src/i18n.rs` as a field of `Strings`; `EN` is the only locale in v1 and `t()` returns it. Another locale is one more `Strings` value, so a missing translation is a compile error.
- Strings that carry values are templates with named `{placeholders}`, filled by `fill`, so a translation can reorder them.
- Language-neutral glyphs (↑, ↓, ×) and separators stay in the views.
- `error_message` maps `ErrorCode` to text (spec section 15). Codes that are complete on their own (`NotFound`, `Conflict`, `Cancelled`, `Keychain`, `AiNotConfigured`, `AiConsentRequired`, `AiCancelled`) get a fixed i18n string. For the others the backend message is the specific, actionable part (which field failed validation, what was wrong with an imported file), so the UI shows it as sent. The match has no wildcard, so a new code has to choose.
- A unit test scans the other UI source files and fails on string literals that look like user-facing text.

## ADR-051 — Style tab (M3)

- The editor's left pane has two tabs, Content and Style (spec section 12.2). Switching only hides the other tab, so fields keep their state. The Variants and Checks tabs come with their own work.
- `list_templates` returns the embedded `manifest.json` files as `TemplateManifest` (spec section 10.2). The sliders take their ranges from the CV's template manifest. A test keeps the `classic` manifest's ranges equal to `TemplateOptions`' clamping ranges, which the backend still applies on save.
- Paper size and date style are radio groups. Locale is a select with English only (ADR-011). The accent is a colour input with a "Use black" button that sets it back to `None`, because a colour input cannot show "no colour".

## ADR-052 — Editor undo/redo and shortcuts (M3)

- The editor keeps up to 100 whole-`Cv` snapshots in memory for undo, separate from database snapshots (spec section 12.1). Edits less than a second apart are one step, so a typed word undoes at once. Any new edit clears redo. Closing the editor drops the history.
- Undo and redo restore the snapshot and then preview and autosave like any edit. Fields that read the model only once (dates, skill lines) are rebuilt after a restore.
- `Ctrl+Z` undoes, and `Ctrl+Shift+Z` or `Ctrl+Y` redoes. `Ctrl+S` saves now and `Ctrl+E` exports a PDF. Cmd works in place of Ctrl. The editor's undo replaces the browser's per-field undo, which would not match the CV model. Undo and Redo buttons in the header do the same.

## ADR-053 — Drag-and-drop reordering with pointer events (M3)

- Sections, entries, bullets, skill groups and language rows can be dragged by a handle (spec section 12.10). The handle captures the pointer, finds the item of the same list under it with `elementFromPoint`, outlines it, and on release moves the dragged item to that item's place. Each list is one parent, so an item never moves to another parent.
- Pointer events are used instead of HTML5 drag and drop, because Tauri's file-drop handling turns HTML5 drag and drop off in the Windows WebView, and instead of SortableJS, so there is no JavaScript to vendor.
- Dragging near the top or bottom of the form scrolls it. The Move up/Move down buttons stay as the keyboard alternative, and the handle is hidden from assistive technology.

## ADR-054 — Content tab: add section menu, custom sections, collapsing, locked, summary counter (M3)

- One "Add section" menu below the sections replaces the per-kind add buttons. It offers Experience, Education, Projects, Skills, Languages, Certifications and Custom (spec section 12.3), and each new section starts with one empty item.
- Custom sections are edited like entry sections, with their title edited in the section heading.
- Each section has a collapse toggle. Collapsing only hides the section's contents in the form; it does not change the CV or the preview.
- Each entry has a "Locked" checkbox. Its tooltip, also given to screen readers, says that locking protects the entry's facts from AI suggestions (spec sections 4.4 and 12.3).
- The summary shows a character counter against the lint limit (`SUMMARY_MAX_CHARS`, 600). It turns red past the limit, and the lint check still reports it.

## ADR-055 — Preview zoom and diagnostics strip (M3)

- A bar above the preview has "Fit width" (the default: pages as wide as the pane, up to the existing maximum) and "100%" (the page's real width at 96 CSS pixels per inch, from the CV's paper size; the pane scrolls sideways if needed). The zoom is not saved.
- Template messages from the newest preview show in a collapsible strip above the pages, with their severity: warnings from a successful render (such as missing glyphs) and the diagnostics a failed render carries in its error details. The strip is hidden when there are none.

## ADR-056 — Local log file (M3)

- The desktop shell logs with `tracing` to `pinaxcv.log` in Tauri's app log directory (`docs/SECURITY.md` lists the paths). Release builds log at info level and debug builds at debug level.
- Each command logs its name, duration and, on failure, the error code. Arguments and error messages are never logged, because both can quote CV content. A database that fails to open is logged without the error text for the same reason.
- A panic hook logs the panic's location and message, cut to 300 characters, then runs the default hook.
- At startup a log over 1 MB is renamed to `pinaxcv.1.log`, replacing the older one, so at most about 2 MB is kept. If the log cannot be opened, the app runs without one.
- Opening the log folder from the app comes with the Settings screen (`open_data_dir`, spec section 10.2).

## ADR-057 — End-to-end smoke test with tauri-driver

- A CI job on `ubuntu-22.04` and `windows-latest` builds the app and drives it through `tauri-driver` (WebKitWebDriver under Xvfb on Linux, `msedgedriver` matching the WebView2 runtime on Windows). The test creates a CV, types a name and email, waits for a preview page and exports a PDF, then checks the file starts with `%PDF` (spec section 14).
- The test is Rust (`crates/e2e`) with a small W3C WebDriver client over `ureq`, so the repository stays Rust-only. `cargo test` skips it unless `PINAXCV_E2E_APP` is set.
- WebDriver cannot drive native file dialogs, so the shell's `e2e` cargo feature replaces the save dialog with one that writes into `PINAXCV_E2E_EXPORT_DIR`. Only the e2e job enables the feature; release builds do not contain it.
- On Windows, msedgedriver passes its debugging port through `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, which WebView2 ignores when the app sets its own browser arguments, as wry always does. The `e2e` build appends that variable's arguments to wry's defaults in the window config.
- The `tauri-action` build from spec section 14 belongs to the packaging milestone (M8).

## ADR-058 — Import wizard: parse, match, commit (M4)

- Importing is three commands (spec sections 9.5 and 10.2). `import_parse` opens the backend's file dialog (PDF and XML for now), reads at most 20 MB, runs the importers (Europass first, then the PDF text importer, ADR-047) and returns an `ImportPreview`: what was read, with fresh IDs, and the warnings. The parsed import stays in memory under its `preview_id`; the four newest are kept. Nothing is saved yet.
- `import_match(preview_id, cv_id)` returns the contact fields that both sides fill with different values and the suggested entry matches (same kind of section, organisation, title and start year).
- `import_commit(preview_id, target, use_imported, entries)` saves a new CV, or merges into an existing one. A merge checks the CV's revision, applies the user's choices (each conflicting field: keep mine or use imported; each imported entry: skip, add as new, or replace an existing entry, which keeps that entry's ID), takes an `import` snapshot and saves. Empty fields are always filled, and new skills, languages and links are always added. The preview is dropped once saved.
- The format is detected from the file's content, not chosen by the user, so the spec's `kind` argument is not needed yet. JSON Resume (#44) and LinkedIn ZIP (#45) add their extensions and detection to the same commands.
- The wizard replaces the CV list while it is open: summary, warnings, then "A new CV" (title, defaulting to the imported name) or "Merge into an existing CV" with the review. Matched entries default to Replace, others to Add as new, and conflicting fields to Keep mine. The end-to-end build's dialog reads `PINAXCV_E2E_IMPORT_FILE`.
- The `SaveDialog` trait became `FileDialog` with an open method, so the shell keeps owning every path.

## ADR-059 — JSON Resume importer (M4)

- `import_json_resume` maps the JSON Resume schema as spec section 9.1 says. The file is read as untyped JSON, so unknown fields are ignored and values of the wrong type are skipped instead of failing the import. A JSON object without any schema key is `UnsupportedFormat`; broken JSON is `Malformed`.
- Older keys are accepted where the schema renamed them (`company` for `work.name`). `volunteer` becomes a custom "Volunteering" section, education `courses` become bullets and `score` the description. Awards, publications, interests and references are not imported, with a warning each. References are never imported, because they hold other people's details.
- Every text value is NFC-normalized, has tabs and other whitespace turned into spaces, is stripped of the remaining control characters (line breaks kept in summaries and descriptions) and is capped at 10,000 characters; each list keeps its first 200 items, with a warning. An entry with neither a title nor an organization is skipped, with a warning. `import_json_resume` enforces the 20 MB input cap itself; that cap and serde_json's nesting limit bound the rest, and nothing in the importer can panic on input.
- `import_any` sends anything that starts with `{` to this importer, so the import wizard (ADR-058) picks JSON Resume up by adding the `json` extension to its dialog.

## ADR-060 — LinkedIn data export (ZIP) importer (M4)

- `import_linkedin_zip` reads the profile CSVs from spec section 9.3 straight from memory with the `zip` crate (deflate only, no other codecs), and never extracts to disk. Files are matched by name without their folder, case-insensitively, through an alias table (`Email Addresses.csv`, `Email_Addresses.csv`, ...). Other files are not read; their names are listed in one warning.
- Columns are found by header name (case-insensitive, BOM trimmed, with aliases). The header row is the row, among the first 20, holding the most known columns (the earliest on a tie), which skips the notes preamble some LinkedIn files have even when a preamble line matches one column. A file with rows but no header, a CSV that stops parsing part way, and rows past the cap each give one warning naming the file.
- The archive is refused when any entry has an unsafe path (`..`, absolute, drive letter, NUL), when it has more than 2,000 entries, or when a CSV unpacks past 5 MB or all read CSVs past 20 MB. Names are checked from the central directory before any entry is decompressed, and only the CSVs that are read are unpacked. Sizes are counted while reading, not trusted from the ZIP headers. Each CSV keeps 500 rows and each value 10,000 characters, NFC-normalized, with tabs and line breaks turned into spaces (descriptions keep their line breaks) and other control characters removed. File names in warnings are cleaned the same way and cut to 100 characters.
- Positions are sorted newest first; an empty "Finished On" marks the job as current. Descriptions split into bullets on lines and on `-`, `•`, `*`; one paragraph over 300 characters stays a description, with a warning to review it. Skills become one unlabelled group, because the section heading already says Skills. The email is the primary confirmed address, then any confirmed one; an unconfirmed address is never used.
- `import_any` sends anything with a ZIP signature to this importer, so the import wizard (ADR-058) only needs the `zip` extension added to its dialog.
